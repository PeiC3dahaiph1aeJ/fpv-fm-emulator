# FPV FM Emulator for Pluto+

**English** | [Українська](README.uk.md)

A generator of test **analog FPV video with FM modulation** built on the
**ADALM-Pluto+** SDR. It builds realistic composite video (color test patterns),
frequency-modulates a carrier with it and transmits over the air — so you can test
**analog FPV detectors** across different bands, channels and power levels, either
with scenarios (band sweep, power ramp, several "drones" at once) or manually.

![Main application window](docs/screenshot.png)

> This is a **bench test-signal generator**. It transmits over the air — use it only
> in a shielded environment / on permitted frequencies, with the proper approvals.
> Responsibility for on-air operation rests with the operator.

## What it does

A real analog FPV transmitter frequency-modulates a carrier with composite video from
the camera. An FPV detector receives that FM video and detects the presence of a drone.
The emulator reproduces exactly that signal:

```
color test pattern → composite video (CVBS, PAL50/NTSC60) → FM → IQ → Pluto TX
```

**Important (verified on a real detector):** the detector looks not only at power
(RSSI) but at the **modulation profile**. That is why a **realistic FPV profile** is
generated by default — color bars with a 4.43 MHz subcarrier + wide FM, occupied
bandwidth ~17 MHz, just like a real VTX. A narrow B/W signal gave a high RSSI but was
recognized poorly.

## Architecture

The core does not depend on hardware — it can be run and tested offline.

```
fpv_emulator/
  bands.py        band/channel tables + guard beyond HW limits
  video.py        composite video (PAL50/NTSC60), luma + color patterns, chroma
  fm.py           FM modulation baseband → IQ, conversion to int16
  signal_gen.py   video+FM → frame (cyclic) IQ; multi-drone
  backends.py     IQ sinks: Pluto (pyadi-iio) | soapy (HackRF/Lime/…) | file | null
  scenarios.py    scenario engine (static/sweep+pause/power_ramp/multi_drone), live power
  config.py       loading/validation of YAML scenarios
  probe.py        detection of the Pluto chip and its tuning limits
  cli.py          command-line interface
gui/app.py        desktop GUI (PySide6): manual control + scenarios + preview
config/
  bands.yaml      channel frequencies (editable)
  scenarios/*.yaml example scenarios
scripts/probe_pluto.py   standalone hardware probe
tests/            offline core tests (pytest, 30 of them)
```

## Installation and start (Windows — two clicks)

**The main tool is the GUI.** No terminal is needed for day-to-day work:

1. **`setup.bat`** — double-click it **once**. It creates the `.venv` environment and
   installs everything needed (numpy, PySide6, pyadi-iio…).
2. **`run_gui.bat`** — double-click to **start the GUI**. The main window opens
   (startup errors, if any, are shown in a dialog).

> Tip: right-click `run_gui.bat` → create a desktop shortcut / pin it to the taskbar —
> and startup becomes a single click.

### GUI — what is inside

It opens right away with a working profile (color_bars, 20 MSPS, PAL50, backend
`pluto`). Everything is controlled with the mouse:
- **Output:** backend (`pluto` / `soapy` for HackRF and others), URI/device, the
  "Probe Pluto" and "List SDRs" buttons.
- **Frequency:** band/channel or a manually entered carrier.
- **Signal:** standard, pattern (preview in color), sample rate, deviation.
- **Power:** slider, **changes at runtime** while transmitting.
- **Mode:** manual carrier or a ready-made scenario; Start/Stop; event log.
- **Language:** a selector in the **Output** panel switches the interface between
  English and Ukrainian; the choice is remembered between sessions.

To transmit: choose backend `pluto` (or `soapy`), a frequency → **Start**.

## Terminal (CLI) — for automation only

The GUI covers everyday work; the CLI is handy for scripts. Run it through `.venv`:

```bash
.venv\Scripts\python.exe -m fpv_emulator.cli probe
.venv\Scripts\python.exe -m fpv_emulator.cli tx --backend pluto --scenario sweep_ranges
.venv\Scripts\python.exe -m fpv_emulator.cli tx --backend pluto --freq-mhz 1200 --pattern color_bars --gain 0
.venv\Scripts\python.exe -m fpv_emulator.cli gen --pattern color_bars --sample-rate 20e6 --out frame.iq
.venv\Scripts\python.exe -m fpv_emulator.cli list-bands   # also list-patterns | list-scenarios | list-devices
```

The interface language is selected with the `--lang en|uk` flag (English by default);
the `FPV_LANG=uk` environment variable works as a fallback default.

Manual installation (instead of `setup.bat`):
```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt -r requirements-hw.txt
```
The native **libiio** must be present in the system (Linux: `apt install libiio0 libiio-utils`).

## Video standards and patterns

**Standards:** `PAL50` (312 lines, 50 Hz fields) and `NTSC60` (262 lines, 60 Hz) —
progressive 288p/240p. It is exactly the 50/60 Hz field rate (and not 25/30) that
removes the vertical roll of the picture on the detector's monitor. The old names
`PAL`/`NTSC` are mapped automatically to `PAL50`/`NTSC60`.

**Luma patterns (B/W):** `bars`, `smpte75`, `ramp`, `crosshair`, `grid`, `checker`,
`multiburst`, `white`, `gray`, `black`.

**Color patterns (realistic FPV):** `color_bars` (75%), `color_bars100` — with a
4.43 MHz subcarrier (PAL) / 3.58 MHz (NTSC), burst and chroma modulation. They require
`fs ≥ ~13 MSPS` (in the GUI it is raised automatically to 20).

## Scenarios (YAML)

A common `signal:` block (standard, pattern, sample_rate, deviation_pp_hz, gain_db),
then a block per type. Examples are in `config/scenarios/`.

| Type | Purpose |
|-----|-------------|
| `static` | a single carrier (channel/freq_mhz, hold_s) |
| `sweep` | stepping through channels/**bands with a step** (`ranges`), with an optional **pause** (`pause_s`) |
| `power_ramp` | a drone approaching/departing (start_db→end_db, mode: up/down/pingpong) |
| `multi_drone` | several carriers at once (drones[{pattern, offset_mhz, level_db}]) |

Sweep across bands:
```yaml
sweep:
  ranges:
    - { start_mhz: 5650, stop_mhz: 5950, step_mhz: 20 }   # e.g. 5.8 GHz FPV
  dwell_s: 15    # transmitting on the frequency
  pause_s: 5     # silence (RF off) between frequencies
```

## How it works (DSP)

1. **Composite field** (`video.py`): one field period of 288p/240p with correct line
   timing and vertical sync (50/60 Hz). For color, a subcarrier + burst + chroma are
   added (U/V; for PAL — the V phase is switched line by line).
2. **FM** (`fm.py`): `iq = exp(j·2π·∫ dev·v dt)`. Centering (subtracting the mean)
   ensures phase continuity at the seam of the cyclic buffer.
3. **Cyclic buffer**: one field is uploaded as `tx_cyclic_buffer` and repeated inside
   the device. Frequency/power changes happen on the fly; a pattern change means a
   re-upload.
4. **Live power**: the GUI slider stores the value and the worker thread applies
   `tx_hardwaregain` (libiio is touched from a single thread only).

**Nyquist:** the peak excursion `±deviation/2` (+ multi-drone offsets) must be < `fs/2`,
otherwise the signal folds back (a warning is issued).

## Hardware notes (Pluto+)

| Type | Chip | Range | 5.8 GHz |
|-----|-----|----------|---------|
| Stock | AD9363 | 325 MHz – 3.8 GHz | only through an up-converter |
| AD9361-modded | AD9361 | 70 MHz – 6.0 GHz | directly |

At **5.8 GHz the Pluto output is weaker** (the board is designed for ~up to 3.8 GHz) —
a wide signal there may be marginal. On the lower bands (1–3 GHz) the output is strong.

## Supported SDRs

The core generates IQ independently of the hardware; the transmit backend is selected
with the `--backend` flag (CLI) or in the GUI.

| Backend | Devices | Notes |
|---------|----------|----------|
| `pluto` | ADALM-Pluto / Pluto+ | native (pyadi-iio/libiio), cyclic buffer inside the device |
| `soapy` | **HackRF, LimeSDR, BladeRF, USRP**, Pluto and others | via SoapySDR; the host streams the frame continuously |
| `file` | any (offline) | IQ written to `.iq`/`.npy` |
| `null` | — | dry run without going on air |

SoapySDR examples:
```bash
python -m fpv_emulator.cli list-devices                       # find connected SDRs
python -m fpv_emulator.cli tx --backend soapy --device driver=hackrf --freq-mhz 5800 --gain 0
python -m fpv_emulator.cli tx --backend soapy --device driver=lime --scenario sweep_ranges
```
In the GUI: backend `soapy`, in the "SDR (soapy)" field — `driver=hackrf|lime|uhd|bladerf`,
the "List SDRs" button shows what is available. The power (slider −89..0, 0 = max) is
mapped automatically onto the device's real gain range.

**Caveats:** HackRF — 8 bit, half duplex, max ~20 MSPS, no hardware cyclic buffer (the
host loops the frame). Cheap RTL-SDR dongles **cannot transmit** (receive only).
Diagnostics through RX (probe, RX self-reception) are specific to Pluto.
For installing SoapySDR see `requirements-hw.txt` (pip does not install it).

## Tests
```bash
python -m pytest tests/ -q
```
50 offline tests, no hardware required. They cover: band/channel lookup (including
ambiguous bare names), the HW-range guard, composite video timing and levels, the
color path (subcarrier, burst placement, PAL V-phase alternation), FM invariants and
the continuity of the cyclic-buffer seam, multi-drone summation and its carrier
spacing, the aliasing warnings, and scenario-engine runs against a recording sink
(sweep, the RF-off pause, tune-before-start ordering, power ramp, live power).

---

## Key takeaways
- **RSSI ≠ reception quality.** The detector looks at the modulation profile → a
  realistic wide color signal is recognized, a narrow B/W one is not, despite a high RSSI.
- A field rate of **50/60 Hz** (not 25/30) is mandatory for correct vertical
  synchronization on the detector's monitor.
